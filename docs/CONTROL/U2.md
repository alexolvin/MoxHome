# CONTROL — U2: CLI

**Дата:** 2026-09-14 · **Ветка/PR:** `stage/U2` → `main`

Метод: командный интерфейс по ТЗ_04 §U2 — `app/cli.py`, 9 команд ТЗ
(analyze / translate / job list / status / resume / cancel / validate /
languages / export cards) + опциональные расширения `--wait [SECONDS]` и
`--cefr` (аддитивны, требуемый интерфейс ТЗ не меняют). Запуск —
`python -m app.cli <команда>` (проект не ставится пакетом; конвенция —
как у воркера `python -m app.workers.run`); в `pyproject.toml` добавлен
`[project.scripts] epubtranslator = "app.cli:main"` (entry point для
установки — проверяется V1.10). Воркер — отдельный процесс, CLI его не
запускает (подсказка в выводе translate).

Собственной бизнес-логики нет (U2-1): CLI вызывает те же сервисы, что
API — `create_job` (services.jobs, как `POST /api/jobs`), `scan_book`
(services.analyze, как `POST /api/books` — функция вынесена из
`api._scan_book` в сервис: единый источник, Rule 8),
`views.job_facts`/`progress_facts`/`languages_view` (как
`GET /api/jobs/{id}`/`GET /api/jobs`/`GET /api/languages`),
`JobRepository.list_jobs`/`get`/`request_resume`/`request_cancel` (E3.1),
`read_epub` + `run_epubcheck` (валидация: те же E2.5/E5.7, что стадии
пайплайна), `PairResolver.resolve_pair` (предотбор пары, тот же
механизм, что предпроверка `dc:language` в `create_job`, L0.7).
Контроль — точный импорт-allowlist `cli.py` (12 модулей сервисного
слоя; любое новое `from app.… import …` — падение теста) + наличие
вызовов + поведенческий паритет вывода на тех же сущностях.

`--source` — только предпроверка заявленной пары (L0.2, fail closed):
неподдерживаемая пара → отказ ДО создания (код 3). Язык задания он НЕ
устанавливает — исходный язык определяет детектор L0.5 в воркере
(`run_validating`, тот же путь, что для заданий из API).

Коды выхода (U2-2): механизм `AppError.exit_code`
(`app/core/errors.py`): 0 — успех; 1 — неуспешное задание
(FAILED/CANCELLED/INTERRUPTED) либо прочие; 2 — ConfigurationError
(конфигурация); 3 — InputValidationError (валидация входа); 4 —
LLMUnavailableError; 5 — OutputValidationFailed. «Успешный код выхода
при неуспешном задании — дефект»: исход задания отражают
`translate --wait` (опрос БД — тот же источник, что UI; timeout → 1)
и `job status` (терминальный FAILED/CANCELLED/INTERRUPTED → 1; статус
и причина — verbatim).

`validate` = `read_epub` (структура: не-ZIP/пустой/mimetype/container/
OPF/spine → код 3, внятное сообщение) + `run_epubcheck` (недоступен →
код 2, fail closed, Rule 6; FATAL/ERROR → код 3 + первые 20 строк в
stderr; иначе → 0 + версия и счётчики).

`export cards`: только для заданий COMPLETED/COMPLETED_WITH_WARNINGS
(иначе JobStateError → 1); имена файлов — `card_export.CARDS_FILES`
(единый источник: писатель S5, `GET /api/jobs/{id}/result`, CLI — одна
таблица).

Прогон: `python tests/u2_evidence.py`, тесты — `pytest
tests/test_u2_cli.py` (T-U2-1…T-U2-4; воркер — реальный subprocess
`--loop` (D69), LLM — MockLLMServer, CLI — реальный subprocess
`python -m app.cli`; stdout процесса CLI — `-u`, «задание: <id>»
виден live). Verbatim-захваты: `docs/CONTROL/evidence/U2/`.

## Метрики и механизмы (измерено vs не проверено)

**Измерено** (артефакты в колонке «Артефакт»):
- 0 дублирования бизнес-логики: точный импорт-allowlist `cli.py`
  (12 модулей сервисного слоя) + 9/9 вызовов сервисов API +
  поведенческий паритет (analyze 4/4, languages 6/6 и 11/11) — U2-1;
- 8/8 сценариев кодов выхода (0/0/1/1/2/3/3/3) + причина FAILED
  verbatim; export cards 0 (3 карточки) / 1 (гейт) — U2-2;
- 2/2 направления видимости заданий CLI↔UI по одному БД — U2-3;
- validate: повреждённый → 3 + «не является ZIP-архивом», валидная →
  0 + «EPUBCheck v5.3.0: 0 FATAL, 0 ERROR, WARNING 0» — T-U2-4;
- регрессия U1 (рефакторинг `api.py`: `scan_book` в сервис,
  `_RESULT_PATTERN` из `CARDS_FILES`) — 10/10 тестов U1 зелёные;
- дефект ядра, пойманный полным прогоном при верификации U2
  (D71): `load_dotenv` в `load_settings` мутировал `os.environ` —
  `SERVER_AUTH_SECRET` U1-профиля «auth» перетекал в профили U2
  (401 на каждом API-вызове; изолированный запуск U2 — зелёный);
  исправлено в `app/core/config.py` (`dotenv_values`, без мутации,
  приоритет os.environ > файл сохранён) — последовательная регрессия
  U1+U2 — 14/14;
- Тесты: 270/270 (266 + 4 запуска T-U2-1…T-U2-4), ruff 0
  (`app/` + `tests/`), mypy strict 0 (75 файлов).

**Не проверено / ограничения (честно):**
- Коды 4 (LLMUnavailableError) и 5 (OutputValidationFailed) не
  порождаются 8 сценариями ТЗ — классы и маппинг существуют в
  механизме `AppError` (`app/core/errors.py`); сценарий «LLM down»
  отражается исходом ЗАДАНИЯ (FAILED → 1) с причиной as-is, а не
  промежуточным классом — код выхода отвечает на «что с заданием», а
  разделение классов 2/3/4/5 действует на уровне ошибок КОМАНДЫ.
- Подтверждение подозрительной книги (NEEDS_CONFIRMATION) — через UI
  (`/jobs/<id>`): команды ТЗ CLI confirm не включают; CLI при таком
  статусе в `job status` показывает подсказку «через UI /jobs/<id>».
  (В тестах/доказательствах подтверждение идёт через API — человек в
  контуре эмулируется; сам CLI его не вызывает.)
- Команда `epubtranslator` как установленный пакет — не проверялась
  (проект работает через `python -m app.cli`, конвенция проекта;
  entry point `[project.scripts]` добавлен — проверяется V1.10).
- `--wait`/`--cefr` — опциональные расширения за пределами списка
  команд ТЗ (аддитивны); требуемый интерфейс ТЗ — полный.
- LLM — mock-сервер (D3, BLOCKER-1): сценарии FAILED (ConnectError)
  и COMPLETED — на mock'е; поведение с реальным провайдером не
  проверялось (V1.13).
