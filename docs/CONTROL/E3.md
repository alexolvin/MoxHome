## Метрики и механизмы (измерено vs не проверено)

**Измерено** (артефакты в колонке «Артефакт»):
- окно осиротения 0.574 с и порядок переходов kill→recovery→resume (E3-1);
- 44/152 по таблице переходов и отсутствие записи отклонённых в `transitions` (E3-2);
- хэш артефакта и 0 запросов при повторном запуске этапа (E3-3);
- X/Y/Z и share 0.0000% (E3-4);
- 0.392 с до `CANCELLED` и пометка частичного артефакта (E3-5);
- 1 исполнитель из 2, 4 LLM-запроса (E3-6).

**Гарантировано конфигурацией/конструктом, runtime-мерой не проверялось отдельно:**
- ограничение `lease_seconds ≤ 2×heartbeat_seconds` — валидатор конфигурации
  (`Settings._check_lease_heartbeat`), нарушение даёт `ConfigurationError` при старте
  (тест `tests/test_config.py`); в прогонах E3 использовалась верхняя граница 1.0 = 2×0.5.
- атомарность занятия (`UPDATE … WHERE status IN (…) AND (worker_pid IS NULL OR
  lease_expires_at < now)`) — проверена сценарием E3-6, но гонка двух процессов на уровне
  одной строки SQLite дополнительно не нагружалась (одна запись = одно задание).

## Дефект, найденный и исправленный на этапе (Rule 3 — честно)

Heartbeat-поток использовал `sqlite3.Connection` главной нити
(`check_same_thread=True`) → `sqlite3.ProgrammingError`, аренда не продлевалась,
долгое задание ошибочно осиротевало. Исправлено: heartbeat-поток создаёт собственное
thread-local подключение (`Settings.jobs_db_path` — единый источник пути).
Регрессионная защита: в T-E3-1 kill намеренно позже истечения исходной аренды
(задержка 1.5 с > lease 1.0 с) и проверяется `lease_expires_at ≥ t_kill` — без
продления арена на момент kill была бы истекшей.

## Замечания

- **Точка kill по токенам, не по progress.** Замеры показали: движок пишет
  `on_progress(0.4/0.7/1.0)` пачкой в конце фазы (для `complex.epub` все три
  обновления — в течение миллисекунд после последнего fill), поэтому progress
  ненадёжен как сигнал «середина перевода». Надёжный сигнал — токены в БД: они
  flush'ятся после первой завершённой группы (TOC+META), окно до конца фазы ~3 с
  при задержке 1.5 с. Тест ждёт `status=TRANSLATING AND tokens>0`.
- **Группировка движка** (подтверждено замерами): `complex.epub` → 2 группы:
  группа 1 = TOC+METADATA (1 translate + 1 fill), группа 2 = все 3 главы
  (1 translate + 1 fill). Итого 4 запроса на полный прогон.
- **Кэш движка — причина share 0%:** `cache_path` внутри каталога задания
  (`jobs/<id>/engine_cache`), ключ = запрос; завершённые до kill группы на resume
  читаются из кэша (0 токенов), поэтому X+Y ≤ Z.
- **Восстановление — только при старте воркера** (`recover_expired_leases`), по
  истёкшей арене; другого детектора осиротения нет (Rule 8).
- **Очередь:** FIFO + `priority` (DESC, затем `created_at`), одно активное задание;
  занятость = `worker_pid` + `lease_expires_at`, освобождение — при завершении/паузе.
- Job-логи (требование E3.9): `jobs/<id>/job.log`, `errors.log`, `quality.log`
  (создаются сразу, redaction секретов).
